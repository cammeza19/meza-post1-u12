# ADR-001: Capas simples para persistencia; el seam de notificación ya cubre el próximo cambio conocido

## Estado
Aceptado — 2026-11-07

## Contexto
Tras integrar los patrones Chain of Responsibility, Strategy y Observer en el sistema de solicitudes de reembolso de gastos corporativos, corresponde decidir si el proyecto debe migrar a una arquitectura Hexagonal completa (introduciendo interfaces de puerto, adaptadores y mappers para persistencia y notificación) o mantenerse en capas simples (servicio llamando directamente al repositorio JPA).

Actualmente:
1. No existe ninguna necesidad ni plan de cambiar el motor de base de datos relacional (H2 / SQL).
2. El área de Contabilidad anunció que para el próximo trimestre requerirá integrarse mediante una API HTTP externa para ordenar el desembolso de los pagos aprobados.

## Decisión
Se decide:
1. **Persistencia en capas simples:** Mantener la inyección directa de `RepositorioSolicitudesJpa` en `SolicitudReembolsoService`. Introducir hoy un puerto abstracto `RepositorioSolicitudes` con un adaptador JPA secundario y clases mapper intermedias constituiría una abstracción puramente especulativa, violando el principio **YAGNI** (*You Ain't Gonna Need It*).
2. **Notificación desacoplada:** No introducir cambios estructurales adicionales en `procesamiento.notificacion`. La interfaz `ObservadorCambioEstado` ya actúa como el *seam* (costura arquitectónica) necesario. Cuando llegue el momento de consumir la API externa de Contabilidad el próximo trimestre, bastará con actualizar la implementación interna de `NotificadorContabilidad` sin alterar en absoluto `SolicitudReembolsoService` ni los demás observadores.

## Consecuencias

### Positivas
* Se evita la sobreingeniería: no se crean interfaces vacías de único implementador ni código de mapeo innecesario entre entidades JPA y objetos de dominio.
* El único cambio de infraestructura confirmado con fecha real (la integración externa de Contabilidad) ya cuenta con un punto de extensión desacoplado y preparado.
* El modelo cognitivo del código permanece simple y directo para el equipo de desarrollo.

### Negativas
* Si en el futuro surge un requerimiento real de migrar a una base de datos no relacional (ej. MongoDB), el desacoplamiento mediante puerto de persistencia deberá realizarse retroactivamente, aceptando esa deuda técnica de forma consciente.
* Un revisor que busque simetría arquitectónica total (puertos en todas las dependencias externas) podría percibir una asimetría entre persistencia y notificación si no consulta este documento ADR.
