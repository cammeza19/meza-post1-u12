# ADR-001: Capas simples para persistencia; el seam de notificación ya cubre el próximo cambio conocido

## Estado
Aceptado — 2026-11-07

## Contexto
Tras integrar los patrones Chain of Responsibility (RF1), Strategy (RF2) y Observer (RF3) en el sistema de solicitudes de reembolso de gastos corporativos, corresponde decidir si el proyecto debe migrar a una arquitectura Hexagonal completa (interfaces de puerto, adaptadores y mappers para persistencia y notificación) o mantenerse en capas simples (servicio de aplicación llamando directamente al repositorio JPA).

El criterio de la Guía (sección 6.2) es explícito: la arquitectura Hexagonal vale la pena **en sistemas que sobrevivirán 3 años o más con cambios de infraestructura**. Ese criterio se evalúa por separado para cada dependencia externa, con datos de este proyecto:

| Dependencia | ¿Vida útil ≥ 3 años? | ¿Cambio de infraestructura conocido? | ¿Se cumple el criterio? |
|---|---|---|---|
| Persistencia (`RepositorioSolicitudesJpa` sobre H2/SQL) | Probable: reemplaza una hoja de cálculo de Finanzas | **No.** No existe ningún plan, presupuesto ni requisito de cambiar de motor de base de datos | **No** |
| Notificación a Contabilidad | Probable | **Sí.** Contabilidad anunció una integración por API HTTP externa para el próximo trimestre | **Sí**, pero el *seam* ya existe (`ObservadorCambioEstado`) |

## Alternativas consideradas
1. **Hexagonal completa:** puerto `RepositorioSolicitudes` + adaptador JPA + mapper entidad↔dominio, y puerto `PasarelaContabilidad` para la notificación. *Descartada:* duplica el modelo (entidad JPA y objeto de dominio) y agrega ~4 tipos nuevos sin un segundo implementador real de ninguno de los puertos.
2. **Puerto solo para persistencia:** interfaz `RepositorioSolicitudes` implementada por un adaptador JPA. *Descartada:* sería una interfaz con un único implementador y sin driver de cambio (falla el test de explicabilidad: no se puede decir en una oración qué problema actual resuelve).
3. **Capas simples + Observer como seam (elegida):** ver Decisión.

## Decisión
1. **Persistencia en capas simples:** `SolicitudReembolsoService` sigue dependiendo directamente de `RepositorioSolicitudesJpa`, que extiende `JpaRepository<SolicitudReembolso, Long>`. Introducir hoy un puerto de persistencia sería una abstracción especulativa (**YAGNI**) y añadiría indirección sin beneficio (**KISS**).
2. **Notificación sin cambios estructurales:** el paquete `procesamiento.notificacion` ya desacopla el servicio de sus tres suscriptores a través de `ObservadorCambioEstado`, que funciona como el puerto de salida que la Hexagonal pediría. Cuando llegue la API externa de Contabilidad, solo cambiará la implementación interna de `NotificadorContabilidad`; `SolicitudReembolsoService` y los demás observadores no se modifican.
3. **Consecuencia aceptada en el dominio:** como no hay puerto ni mapper, `SolicitudReembolso` actúa a la vez como modelo de dominio y como entidad JPA (anotaciones `jakarta.persistence` añadidas en el commit del Paso 5). El modelo nació puro en el commit de línea base y las anotaciones son solo metadatos declarativos; el dominio no importa ninguna clase de Spring.

## Consecuencias

### Positivas
* No se crean interfaces de único implementador ni código de mapeo entre entidades JPA y objetos de dominio.
* El único cambio de infraestructura con fecha conocida (la integración de Contabilidad) ya tiene su punto de extensión, verificado además por la Regla 4 de ArchUnit.
* Las reglas ArchUnit validan los límites que sí existen (procesamiento sin JPA ni web; controlador solo vía servicio) sin asumir puertos inexistentes.
* El modelo mental del código sigue siendo simple: controlador → servicio → (patrones + repositorio).

### Negativas
* Si en el futuro se requiere cambiar de motor (por ejemplo, migrar a una base NoSQL), el puerto de persistencia deberá introducirse retroactivamente y habrá que separar la entidad JPA del modelo de dominio; se acepta esa deuda técnica de forma consciente.
* El modelo de dominio lleva anotaciones JPA, por lo que no es 100 % independiente de la tecnología de persistencia.
* Un revisor que espere simetría total (puertos en todas las dependencias externas) puede interpretar la asimetría persistencia/notificación como inconsistencia si no lee este ADR.

### Señal para revisar esta decisión
Un requisito real y fechado de cambiar de motor de base de datos, la aparición de un segundo mecanismo de persistencia (p. ej. un archivo de exportación que deba leerse como repositorio), o la necesidad de probar el servicio sin Spring Data.
